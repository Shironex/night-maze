# A shader asks for the location of a uniform once and remembers it by name
Status: accepted (2026-10-12)
Code: src/gfx/Shader.hpp, src/gfx/Shader.cpp, src/gfx/RenderStats.hpp

Context: Every setter of `gfx::Shader` called `glGetUniformLocation` with the name of the uniform. The counters of the frame measurement showed 5,136 such lookups in a frame on Normal and 8,877 on Hard, although a frame on Normal uses only 134 different pairs of program and name.
Decision: `Shader::uniformLocation` keeps the answers in a `std::vector` of pairs of the name and the location, searched from the front, and asks OpenGL only for a name it has not seen. The answer -1 for a name the program does not have is kept too. The list is emptied wherever the program is replaced or given away: a successful `reload`, the move constructor and the move assignment. The setters keep their signatures and stay `const`, so the list is `mutable`. The counter of uniform lookups now counts only the questions to OpenGL.
Why: The search compares the stored names with a `std::string_view`, so a hit builds no `std::string` and allocates nothing. A program uses a few dozen names at most, so the linear search is as quick as a tree. The first version was a `std::map` ordered with `std::less<>`; it was replaced (2026-10-15) because moving a `std::map` may allocate in the standard library of Visual Studio, and clang-tidy (`bugprone-exception-escape`) rejected it in the `noexcept` move constructor. A vector moves without allocating. The pointer of the string literal as the key was rejected: it is faster, but two places that write the same name may hold different pointers, and a name built at run time would be found by accident or not at all.
Cost and revisit: A hit is a search through the names one program uses, with string comparisons. Measured on an Apple M3 (2026-10-12, Release, vsync off, window of 1280 x 720, `--play --calm --seed 7`, three runs of each build in turn): the lookups of a frame went to 0 on both difficulties, and 134 for the one frame after all shaders were reloaded. The median CPU render time went from 4.97 to 4.86 ms on Normal and from 6.47 to 5.77 ms on Hard, but the samples of one build spread over 1 ms on Normal and 3 ms on Hard, so the gain is inside the noise on this machine. The driver of Apple answers a lookup quickly. I reopen this if a profile shows the tree search itself: then the setters take a location fetched once by the renderer.
